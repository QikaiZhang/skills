# Real World Coding Workflow

## 核心目标

让 AI 像熟悉项目的工程师一样参与开发，而不是一次性生成一份看似完整的代码：

```text
理解系统 -> 对齐规范 -> 明确范围 -> 分析风险 -> 编写 SPEC ->
最小闭环 -> 分阶段实现 -> 验证 -> 复盘
```

核心原则：

> 代码应该像这个项目原本就会这样写，而不是像 AI 自己认为“应该这样写”。

总体优先级为：

```text
用户意图 > 项目硬性规则 > 现有实现和惯例 > 已确认的 SPEC > 通用工程实践 > AI 偏好
```

不得因为“更优雅”“更现代”或“更抽象”而违反项目已有规则。

## 项目上下文优先

开始非平凡任务前，先检查项目目录结构、入口、调用链、数据流、相似实现、Proto/OpenAPI/Schema、数据库、Redis、错误处理、日志、测试、代码生成、配置、依赖和特殊规则。

项目规则按以下顺序发现：

1. 若当前项目存在 `references/PROJECT_RULES.md`，必须优先读取。
2. 再读取项目已有的 `context/project-context.md`、`project-context.md` 或其他明确指定的项目规则文件。
3. 读取适用的公司级上下文，例如本 Skill 的 [context/company-context.md](context/company-context.md)。
4. 用实际代码验证文档是否仍然有效。

`PROJECT_RULES.md` 是项目知识，不是通用规范。它可以记录 Proto、Extism、数据库分页、Redis Key、API 命名、错误码、日志、配置、生成工具、依赖限制和测试命令等约束。

如果规则与实际代码冲突，必须报告冲突及影响，不得静默选择一方。用户明确要求与项目硬性规则冲突时，展示请求、规则和后果，再执行用户有意作出的覆盖决定。

## 代码自然融入与可读性

可读性首先服从项目本地一致性，同时满足以下约束：

- 复用项目已有的命名、缩写、目录、分层、错误处理、日志和测试模式；不要单独引入另一套风格。
- 优先使用清晰的控制流和有意义的局部命名；避免为了“通用”引入当前需求不需要的抽象、接口、回调或配置。
- 一个函数承担的职责应能从名称和调用关系中理解；当函数同时混合校验、业务决策、持久化和外部副作用时，按项目惯例拆分或说明边界。
- 注释解释“为什么”而不是复述代码；只为业务规则、兼容性、并发假设、外部系统行为和临时方案添加必要注释。
- 不通过压缩代码、过度嵌套、隐式副作用、魔法值或难以追踪的链式调用换取少几行代码。
- 不为了可读性单独重构无关历史代码；发现既有问题时按风险来源分类，并保持当前范围。
- 代码完成后检查新增代码是否能被项目维护者沿着入口、数据流和错误路径读懂。

## 生成代码与源头

识别 `.proto`、OpenAPI、数据库 Schema、SQL generator、GraphQL Schema、ORM 配置、Mock generator 等源头。存在生成流程时：

```text
源定义 -> 项目生成命令 -> 生成代码 -> 应用实现
```

修改源定义并运行项目既有生成命令，不手工维护生成产物。高影响 Proto 变更还必须检查所有调用方、兼容性、消费者顺序、版本或兼容窗口、弃用、发布和回滚，并在改动契约前获得用户确认。

## 任务路由

按风险、可逆性、受影响模块、数据/API 影响、并发、安全和不确定性分类，不按代码行数分类：

- **FAST**：已知根因、局部且低风险的修改。读取 [workflows/fast.md](workflows/fast.md)。
- **NORMAL**：普通多文件功能或模块开发。读取 [workflows/normal.md](workflows/normal.md)。
- **DEEP**：架构、Schema、迁移、跨服务、契约、并发、安全或高影响依赖变更。读取 [workflows/deep.md](workflows/deep.md)，在决策门前等待确认。
- **DEBUGGING**：根因未知、需要证据的故障定位。读取 [workflows/debugging.md](workflows/debugging.md)，先证据后修复。

已知根因且局部低风险的 Bug 走 FAST；仅凭现象猜测、需要复现或可能修复症状时走 DEBUGGING。任务中途若触及外部契约、生成源、持久化 Schema、并发/安全路径或明显扩大范围，立即升级工作流。

## 范围、风险与验证

NORMAL 和 DEEP 任务必须明确要修改、要新增、受影响以及刻意不修改的文件或组件。禁止静默加入无关重构、依赖升级、重命名、目录调整、配置变更或历史问题清理。范围需要扩大时，说明原因、更新 SPEC、重新评估风险，并在高影响情况下请求确认。

对非平凡任务使用 [templates/spec.md](templates/spec.md) 和 [templates/risk-analysis.md](templates/risk-analysis.md)：将问题分类为 `Existing`、`Introduced`、`Amplified`，并按 P0-P3 排序。P0/P1 必须在完成前解决；P2 修复或明确记录延期原因；P3 历史问题不得自动纳入当前范围。

使用 [templates/verification.md](templates/verification.md) 验证最小完整业务闭环，而不是只验证编译或 HTTP 200。明确区分“已实现”和“已验证”，未执行的命令不得声称已执行。使用 [templates/checklist.md](templates/checklist.md) 作为状态板，而不是审批仪式。

## 知识沉淀

可以识别长期有效的项目规则，例如分页、Proto 生成、Extism 路径、Repository 边界和测试命令；但不得自动修改项目上下文。只有用户明确授权时，才将临时发现沉淀为长期规则。
